# Frost landing page

A standalone, responsive landing page based on the supplied mockup. It includes a sample-file demo with browsing, list/grid views, filename search, Quick View, and light/dark appearance. The demo contains illustrative data only and never connects to Frost's file APIs.

The deployable bundle is `dist/`, generated by `node build.mjs` from this directory. The build uses only Node built-ins and fetch, with no npm install. Fonts are bundled under `assets/`, with their license.

The landing page has a WebGL vapour effect across the full viewport. Its fixed canvas is transparent and ignores pointer input. Cursor segments deposit momentum and two independently fading trail weights. A blurred flow texture and nested gradient noise transport the previous state. Rainbow colour comes from velocity; there is no density outline or artificial lens boundary.

`page-scene.js` draws the hero text into a transparent scene texture using its live DOM layout and styles. The shader samples this scene nine times along the flow. The interactive preview is excluded from scene capture, so its rows and icons cannot stretch into the wake. Other page content receives a transparent colour overlay.

The captured elements use `data-vapour-text` or `data-vapour-scene`. Their HTML remains in layout and in the accessibility tree. The canvas supplies their appearance only while a trail is visible. Pointer presses, keyboard input, text selection, Find and Quick View restore the real HTML. The scene renderer supports this page's text and demo elements; it is not a general HTML screenshot library. It captures no external content and uses no page-capture dependency.

The interactive preview is an exception to the HTML visibility rule. CSS keeps `#app-demo` opaque and visible above the vapour canvas, so the preview itself shows no refraction or rainbow overlay. It remains observed for layout changes and the existing interaction pauses. The simulation and shader calculations and their tuning remain at checkpoint `4fdf184`. Versioned stylesheet and module URLs load this change together rather than reusing earlier cached modules.

`page-vapour.js` controls mounting. `intensity` and `refraction` remain at 1. The current tuning uses `flowSpeed: 0.7` to slow the existing wake independently of cursor input, `lifetime: 1.2` to retain momentum and trail weights longer, and `minRadius: 6` CSS pixels to make gentle strokes cover the simulation grid consistently. Fast-stroke radius scaling is unchanged. The colour window includes more of the moving folds, with reduced gain to keep the expanded coverage translucent.

`vapour-shaders.js` contains the independently written shaders, based on the supplied reverse-engineering analysis. `vapour.js` handles GPU resources, input and the render loop. The simulation runs at 60 updates per second, with cursor impulses measured in seconds and simulation pixels. Half-float buffers use continuous exponential weight decay and a smooth visibility fade. The byte-texture fallback retains its minimum positive/negative weight changes. The CPU stop condition follows the storage format's decay and rounding, and shares the shader's invisible threshold. No Lusion assets or runtime libraries are included.

The effect loads for a fine pointer with hover when reduced motion is off. It stops drawing once the trail fades, clears when the tab becomes hidden, and resumes on fresh pointer movement. Scrolling transports the existing wake with the page and refreshes the scene's viewport positions. Touch input is ignored. Unsupported WebGL, missing canvas text-spacing support, or initialization/context failures leave the normal HTML visible. The canvas uses quarter-resolution simulation buffers, eighth-resolution blurred flow buffers, and a display capped at 2× pixel density and 2560 × 1536. Layout changes, font loading and demo updates refresh the scene texture. Printing uses the normal HTML.

## Vercel deployment

Import [0atxl/frost](https://github.com/0atxl/frost) through Vercel's Git integration. Use these settings:

| Setting | Value |
| --- | --- |
| Root directory | `landing` |
| Framework preset | Other |
| Node.js version | 24.x |
| Build command | `node build.mjs` |
| Output directory | `dist` |
| Install command | Skip, as set by the empty `installCommand` in `vercel.json` |
| Production branch | `main` |
| Include source files outside root directory | Off |

Only the allowlisted static files in `dist/` deploy. There are no functions, filesystem APIs, app server, parent dependencies, or runtime GitHub credentials. The `.openai` directory is excluded, and the existing Sites project is independent. Normal updates come from Git pushes; keep the Vercel Git integration enabled.

The build anonymously reads GitHub's public repository and latest stable release API, then downloads `SHA256SUMS`. It writes `release.json` with the version, release URL, available supported archive assets and SHA-256 values, and renders the download link directly into HTML. No browser request or GitHub token is required. It rejects drafts, prereleases, incomplete assets and inconsistent hashes. If no public downloadable release exists or GitHub is unavailable, it renders an honest source-install state. Raw source previews retain the source-install button.

The install card links to the `frost` AUR package and shows `yay -S frost`, followed by `frost`. The existing expandable requirements area also covers paru, a manual AUR build, the current Linux archive, and source installation. Archive commands use the same release metadata as the download button so their version stays current.

## Website analytics

The landing page uses the [plain HTML integration for Vercel Web Analytics](https://vercel.com/docs/analytics/quickstart). Its queue and deferred `/_vercel/insights/script.js` script are in `index.html`; no npm package or application dependency is needed. Enable Web Analytics for the Frost project in the Vercel dashboard before redeploying so Vercel adds the analytics routes.

Analytics measures visits to the hosted landing page. The local file manager has no analytics script, and its files and file operations remain local. There are no custom events that send demo searches or filenames.

## Refresh after a release

In the Vercel project's Settings → Git → Deploy Hooks, create a hook named `Frost stable release` for `main`. Store the full URL as the GitHub repository Actions secret `VERCEL_DEPLOY_HOOK`. Treat this URL as a credential. Never commit it or add it to the website environment.

The Release workflow explicitly calls Website redeploy after publishing the complete stable release. This avoids depending on release events from `GITHUB_TOKEN`, which may not trigger another workflow. The hook rebuilds current `main` so GitHub release metadata is fresh. Git pushes remain the normal source-update mechanism.

If the hook is absent or fails, the release remains published and the website job fails with recovery instructions. Set/fix the secret and run Actions → Website redeploy → Run workflow. You can also redeploy in Vercel's dashboard. Inspect the remote Vercel build result; an accepted hook request alone is not a completed deployment.

Vercel may require the account owner to authorize its GitHub app for this repository. Complete that connection in Vercel's import flow if the repository is unavailable. Do not change repository visibility to work around an account connection issue.

Configuration follows Vercel's [build settings](https://vercel.com/docs/project-configuration/vercel-json) and [Deploy Hooks documentation](https://vercel.com/docs/deploy-hooks).

Keep this website separate from the local Frost service. Only this directory's static files belong in a website deployment.
